## 1. 목적

PQL은 **Sales 파이프라인에서 누락된 세일즈 타겟 재고를 찾는 리스트**다. Sales 딜이 있는 몰은 AE가 이미 크로스셀을 시도한 곳이므로 전부 제외한다. SDR이 시트 메뉴 한 번으로 실행한다는 전제(Apps Script 유지)는 바꾸지 않는다.

## 4. 처리 흐름

메뉴 `PQL 자동화` 아래 두 항목을 둔다.

### 4-1. `PQL 생성`

1. **Pipedrive 조회**: Sales 딜 전체(`/api/v2/deals?pipeline_id=9`, cursor 페이지네이션), 단계·소유자·레이블 이름표. shop_id가 숫자가 아닌 딜은 담당자(persons)·조직(organizations)도 조회한다
2. **CSV 선택·다운로드**: 폴더에서 이름이 `all_subscription_`으로 시작하는 CSV 중 최종 수정 시각이 가장 늦은 파일. Drive API `alt=media`를 20MB씩 Range로 나눠 받는다(UrlFetch 1회 50MB 한도. 원천이 월 약 3MB씩 커진다)
3. **CSV 1회 순회**: 행마다 (a) 역매핑용 키 대조, (b) 공통 클렌징, (c) 타겟 판정을 한다. 통과 행만 메모리에 남긴다
4. **역매핑 판정·반영**: 5장 규칙대로. 높은 확신은 Pipedrive에 쓰고 딜 노트를 남긴다
5. **시트 쓰기**: `deal list` 탭 덮어쓰기(역매핑 반영 후 값), `shop_id 매핑` 탭 갱신, `clean_{yyyyMMdd_HHmmss}` 탭 생성
6. **업로드 파일 생성**: Pipedrive 가져오기 양식의 `pipedrive_up(MMDD).xlsx` (6-1). MMDD는 원천 CSV 파일명에서 딴다
7. **요약 창**: 원천 파일명·수정일, 원천 행 수, 단계별 탈락 수, 딜 제외 수(숫자 매칭/역매핑), 타겟별 행 수, 자동 반영·승인 대기 건수, xlsx 다운로드 링크

Pipedrive 조회를 CSV보다 먼저 하는 이유: 매핑 안 된 딜 253건의 키만 작은 사전으로 만들어 두면, CSV를 한 번만 훑으면서 필터와 대조를 같이 할 수 있다. 전체 CSV 색인을 만들지 않는다.

### 4-2. `승인된 shop_id 반영`

`shop_id 매핑` 탭의 `판정` 열은 드롭다운(`승인`/`거절`)이다. `승인`이고 상태가 `대기`인 행을 Pipedrive에 반영하고 상태를 `반영됨`으로 바꾼다. 반영 방식은 자동 반영과 같다. 한 딜에 승인이 둘 이상이면 반영하지 않고 `실패: 중복 승인`으로 둔다. `거절`한 (딜, 후보 shop) 쌍은 `거절됨`으로 남기고 다음 실행부터 후보로 다시 올리지 않는다.

`PQL 생성`도 시작할 때 이 반영을 먼저 수행한다. 승인해 두고 메뉴를 안 누른 채 다시 PQL을 돌려도 승인이 사라지지 않게 하기 위해서다.

### 5-3. 서비스 라벨

리뷰·업셀·푸시 셋 다 {구독없음, 서비스중단, 프로덕트온보딩중, 빈값}이면 `null`. 아니면 `라이브`로 시작하는 제품을 `알파리뷰, 알파업셀, 알파푸시` 순서로 쉼표 연결한다(라이브 제품이 없으면 빈값, 현행과 동일).

현행과의 차이는 `알파업셀` 표기 하나다. 현행은 업셀 라이브 몰을 공통 필터에서 지웠기 때문에 리뷰·푸시만 봤다. 새 구조에서는 푸시 타겟으로 업셀 라이브 몰이 들어오므로(10/1분 32곳) 업셀을 빼면 라벨이 틀린 제안을 유도한다. 예: 헤트라스(리뷰 과금·업셀 과금·푸시 무료)는 현행 로직이면 `알파리뷰, 알파푸시`가 되어 업셀 제안으로 읽히지만 실제 라벨은 `알파리뷰, 알파업셀, 알파푸시`다.

### 5-4. shop_id 역매핑

대상: Sales 딜 중 shop_id가 빈값이거나 숫자가 아닌 딜.

| 키 | 딜 쪽 | CSV 쪽 | 정규화 |
|---|---|---|---|
| email | 담당자 이메일 | 담당자이메일, 이메일, 결제담당이메일 | 소문자 |
| phone | 담당자 전화 | 담당자전화번호, 전화번호, 고객센터 | 숫자만, `10`으로 시작하는 10자리는 앞에 0, 9자리 미만 무시 |
| name | 딜 제목, 조직명, 딜 `쇼핑몰명` | shop_name, 쇼핑몰명, 회사명(두 열 모두) | (주)·주식회사·㈜·공백·기호 제거, 소문자, 2자 미만 무시 |
| url | 딜 `URL`, 텍스트 shop_id 값 | 대표도메인, 기본제공 도메인, `{mall_id}.cafe24.com` | 스킴·경로·`www.`·`m.` 제거. 텍스트 shop_id가 영숫자면 `{값}.cafe24.com`으로 본다 |

판정:
- **높은 확신**: 걸린 키가 2개 이상이고, 걸린 키들의 후보 교집합이 정확히 shop 1개
- **승인 대기**: 키 1개만 걸려 후보가 1개이거나, 후보가 여럿이라 교집합이 1개로 좁혀지지 않음(모호)
- **매칭 없음**: 기록하지 않음(대부분 앱 설치 전 딜이라 shop_id가 존재하지 않음)

높은 확신은 PQL에서 제외(⑥)한다. 승인 대기 후보 shop은 clean 탭에 남기되 `딜 의심` 열에 딜 ID를 적고, **업로드 xlsx에서는 뺀다**(중복 딜 생성 방지). `거절`되면 다음 실행부터 xlsx에 들어간다. 후보가 여럿인 딜은 후보마다 한 행씩 기록한다.

2026-09-30 실측(253건): 높은 확신 49 / 키 1개 28 / 모호 22 / 매칭 없음 154. 서브마켓(4개 키)·장신몰(전화 후보 2개 ∩ 이름 1개)은 높은 확신으로 잡힌다.

### 5-5. Pipedrive 반영 안전장치

- 숫자 shop_id가 이미 있는 딜은 쓰지 않는다
- 한 실행에서 높은 확신이 100건을 넘으면 자동 반영하지 않고 전부 `대기`로 돌린다(원천 열 밀림 같은 사고로 대량 오기입되는 것 방지)
- 반영할 때 딜 노트를 남긴다: `[PQL 자동매핑 yyyy-MM-dd] shop_id '원래값' → 108903 (근거: email, phone, name, url)`. 텍스트 값은 유입경로 정보라 노트로 보존한다
- `shop_id 매핑` 탭에 딜 ID·딜 이름·원래 값·후보 shop_id·shop_name·일치 키·신뢰도·판정·상태(`반영됨`/`대기`/`거절됨`/`실패: 사유`)를 남긴다. 되돌릴 때 이 탭의 원래 값을 쓴다(되돌리기 메뉴는 만들지 않음)
- 쓰기 실패는 해당 행 상태만 `실패`로 두고 계속한다. PQL 제외는 매칭 결과로 이미 적용된다

## 6. 출력

- `clean_{timestamp}` 탭: 현행 31열에 `타겟`(`서비스 라벨` 앞), `딜 의심`(`서비스 라벨` 뒤)을 추가한다. 앞쪽 열 순서가 바뀌므로 SDR에게 공지한다
- `deal list` 탭: `거래 - 레이블`, `거래 - shop_id`, `거래 - 이름`, `거래 - 소유자`, `거래 - 단계` 5열을 덮어쓴다. 기존 테이블 `표2`의 범위(5,471행)를 넘는 행은 테이블 밖에 쓰인다. 제외 판정은 코드가 하므로 결과에는 영향 없다
- `shop_id 매핑` 탭: 5-5의 열 구성. 실행마다 `대기` 행은 새 결과로 교체하고 `반영됨`·`거절됨`·`실패` 행은 누적한다
- 업로드 xlsx: 6-1

### 6-1. 업로드 xlsx (`pipedrive_up(MMDD).xlsx`)

기존 수동 업로드 파일(`pipedrive_up(0901).xlsx`)과 같은 15열·같은 순서. 대상 행 = clean 탭 행 중 `딜 의심`이 빈 행.

| 열 | 값 |
|---|---|
| 거래 제목 | shop_name |
| shop_id | shop_id (숫자) |
| 상점아이디 | mall_id |
| 호스팅사 | 플랫폼 |
| 월 주문 수 | 최근 30일 플랫폼 주문수 (숫자) |
| 거래 소유자 | `한서연` 고정 (`DEAL_OWNER`) |
| 단계 (파이프라인) | `컨택전` 고정 (`DEAL_STAGE`) |
| 거래 라벨 | 서비스 라벨 (`null` 포함. Pipedrive에 `null` 라벨 딜 848건이 이미 있다) |
| 조직 이름 | 회사명 (CSV의 두 번째 `회사명` 열, 현행 clean과 동일) |
| 이름 | 담당자명 |
| 쇼핑몰명 | 쇼핑몰명 |
| 전화 | 담당자전화번호 (010-XXXX-XXXX 정규화 후) |
| 이메일 | 담당자이메일 |
| URL | 대표도메인 |
| 주소 | 주소1 + 주소2 |

생성 방식: 임시 스프레드시트에 값을 쓰고 Drive export(`format=xlsx`)로 받은 뒤 임시 스프레드시트는 휴지통으로 보낸다. xlsx는 실행한 사람의 내 드라이브에 저장하고 요약 창에 다운로드 링크를 띄운다. 원천 폴더 `05. PQL`에는 쓰지 않는다.

예상 규모(10/1분 CSV, 2026-09-30 딜 기준): 공통 클렌징 ⑤까지 3,224 → 숫자 shop_id 딜 제외 후 425 → 역매핑 높은 확신 제외 + 타겟 판정 후 **약 311곳**(업셀만 223, 업셀·푸시 56, 푸시만 32) — 푸시 무료를 라이브로 본 뒤 **약 285곳**(업셀만 251, 업셀·푸시 28, 푸시만 6). 이 중 `딜 의심` 행은 xlsx에서 빠진다.

## 7. 에러 처리

| 상황 | 처리 |
|---|---|
| CSV 없음 | 알림 후 중단 |
| 필수 열 누락 | 없는 열 이름을 모두 띄우고 중단(현행처럼 조용히 건너뛰지 않음) |
| 다운로드·파싱 실패 | 단계명과 함께 알림 후 중단 |
| Pipedrive 조회 실패 | clean 탭을 만들지 않고 중단. 딜 제외 없는 결과가 나가는 것을 막는다 |
| Pipedrive 쓰기 실패 | 5-5대로 행 단위 기록 후 계속 |
| 토큰 없음 | 첫 실행 때 입력창으로 받아 Script Properties(`PIPEDRIVE_API_TOKEN`)에 저장 |

시트 쓰기는 모든 계산이 끝난 뒤 한 번에 한다. 중간 실패로 반쯤 만든 탭이 남지 않게 하기 위해서다.

## 8. 코드 구조·배포

- 코드 SSOT를 PQL.md 코드블록에서 `src/Code.js`로 옮긴다. `src/appsscript.json`, repo 루트 `.clasp.json`(`rootDir: src`)을 두고 clasp로 배포한다. PQL.md에는 사용법만 남긴다. 이번에 PQL.md와 라이브가 어긋난 원인을 없애기 위한 조치다
- `src/`를 책임별 4개 파일로 나눈다: `Config.js`(설정·타겟 규칙), `Core.js`(Apps Script 서비스를 쓰지 않는 순수 로직), `Io.js`(Drive·Pipedrive·Sheets), `Main.js`(메뉴·실행 흐름). Apps Script는 파일들을 한 전역 스코프로 합치므로, 테스트는 `test/gas.js`가 `Config.js`·`Core.js`를 같은 방식(`vm.runInThisContext`)으로 올려 쓴다
- Advanced Service는 쓰지 않는다(Golden Principle 1). Drive·Pipedrive 모두 UrlFetch
- 설정 상수: `MIN_ORDERS=100`, `PUSH_MIN_ORDERS=500`, `SALES_PIPELINE_ID=9`, shop_id·URL·쇼핑몰명 필드 키, `AUTO_APPLY=true`, `AUTO_APPLY_MAX=100`
- Pipedrive 토큰은 Script Properties에만 둔다. 스크립트 편집 권한자는 열람할 수 있다
